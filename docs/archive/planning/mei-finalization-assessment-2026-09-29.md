# CAMAT MEI finalization assessment — 29 September 2026

**Current status — 2026-10-01:** this is a historical assessment, not the current acceptance report. The shared CAMAT validator and dedicated corpus entry points are now implemented. The pilot source entries, persistent event IDs and three annotation categories/responsibilities have been completed; the measure-11 witness locator was verified through the STIMU reproduction. Namespace-preserving Schematron execution now reports ten official external-IIIF canvas advisories, superseding the earlier zero-warning result below. Publication review remains pending. See [validation responsibilities](../../../validation/README.md#responsibility-boundary), [editorial policy](../../editorial-policy.md) and the [pilot baseline](../../../validation/pilot-baseline.json). Original line numbers and initial findings below describe the earlier snapshot.

**Recommendation: retain official MEI 5.1 CMN and the present header architecture. Finalize the project’s editorial and analytical conventions before treating this pilot as the release template.** No MEI schema violation was found in the example. The main remaining issues concern source attribution, the identity of the encoded musical material, persistent event IDs, and the strength of the publication checks.

The principal object reviewed was [buxtehude_op1_01_sonata_f_major_corr.mei](../../../11_buxtehude_sonatas_final/buxtehude_op1_01_sonata_f_major_corr.mei). This assessment also examined the publication profile, header template, validators, the local CAMAT parser, five selected reference encodings, and BSB IIIF metadata. It did not include a complete note-by-note collation against the images or a full audit of every work in the repository. Edition files and existing tooling were not modified.

**What was verified**

- XML parsing and RELAX NG validation succeeded with `xmllint`.
- The repository schema, `camat_v2/camat/schemas/mei-CMN-5.1.rng`, and a freshly retrieved [official MEI 5.1 CMN schema](https://music-encoding.org/schema/5.1/mei-CMN.rng) have identical SHA-256 hashes: `f6440d5eb59c3e903f2a7a64ea26518646186f8449b86096106846a269eb354b`.
- The root `meiversion="5.1+CMN"` and both XML model declarations agree. Pointing both declarations to the same RNG is appropriate: this official RNG contains embedded Schematron rules.
- Those rules were extracted and executed separately using the ISO Schematron XSLT 2 compiler and SaxonC-HE 13.0. The extracted schema contains 167 patterns, 180 rules, 243 assertions, and one report. Execution produced 18,197 rule firings and zero failed assertions or successful reports.
- The repository checker, with `--publication-profile --check-ppq`, returned zero findings. There are no `ppq` or `dur.ppq` attributes in the pilot.
- An independent scan found 13,009 unique XML IDs and resolved all 690 local fragment-pointer tokens, including `resp` references.
- All 183 measures have corresponding facsimile zones; the ten surfaces and ten page breaks agree. There are 29 further system breaks. The ten IIIF canvases resolve in the retrieved manifest to printed pages 3–12, matching the header.
- Verovio `6.3.0-425dd7b` loaded the file and rendered all 24 pages with no warnings in the load/render run. These are renderer-generated pages, distinct from the ten source pages.
- A separate CAMAT Verovio-backend parsing probe, with tied-note collapsing disabled, returned all 6,858 note rows. Three note rows and one timed chord row have missing source IDs. It also emitted `An expansion cannot be generated with editorial content` while obtaining playback timing. Source-order parsing succeeded; this result does not certify repeat/playback expansion. The pilot has no encoded repeat barlines.

The MEI schema page still presents 5.1 and recommends notation-specific customizations such as CMN. There is no demonstrated reason to change to MEI All or reduce this edition to MEI Basic. Use the official schema plus a versioned CAMAT publication profile and additional checks. An ODD customization can follow if maintaining a formal restricted dialect becomes useful; it is not necessary to address the current findings. [MEI schema guidance](https://music-encoding.org/resources/schemas.html).

**What is already strong**

The header correctly distinguishes the digital file (`fileDesc`), its printed source (`sourceDesc`), the abstract work (`workList`), the encoding process (`encodingDesc`), and significant revisions. Keeping Stiehl’s source editorship separate from the modern encoding responsibilities is particularly useful. The `mdiv/@decls` link to `work.buxwv252`, BuxWV identifier, structured key, source page range, authority records, dated software provenance, and responsibility pointers provide a sound foundation. A compact source description is sufficient here; adopting a large FRBR structure solely because another corpus has one would add little. [MEI metadata model](https://music-encoding.org/guidelines/v5/content/metadata.html).

The GND `auth.uri` values are not errors. MEI permits a complete URI as well as a base URI completed by `codedval`. Choose one convention consistently across CAMAT, but there is no need to rewrite valid complete URIs. [MEI authority attributes](https://music-encoding.org/guidelines/v5/attribute-classes/att.authorized.html).

The BSB manifest corroborates the source title, editor, publication information, identifiers, holding institution, shelfmark, and the stated image license. Separating the MEI-data license from the image terms is appropriate. The provider’s attribution includes both the holding library and BSB; preserve that attribution when presenting images. This checks the recorded provider metadata, not the legal scope of either license. [BSB IIIF manifest](https://api.digitale-sammlungen.de/iiif/presentation/v2/bsb00023199/manifest).

**Resolve before final release**

1. **Describe every source actually used for an emendation.** The annotations at [measure 11](../../../11_buxtehude_sonatas_final/buxtehude_op1_01_sonata_f_major_corr.mei) and [measure 97](../../../11_buxtehude_sonatas_final/buxtehude_op1_01_sonata_f_major_corr.mei) invoke a “1696 print”, but only the 1903 DdT edition is described. Give the base edition an ID, identify the actual additional witness with its repository/shelfmark or digital locator, and connect relevant annotations or readings to it. If the original was known only through a later editor’s report, describe that indirect evidence accurately.

   The year needs verification, not automatic replacement: modern cataloguing commonly dates Op. 1 approximately 1694, while the BSB OCR of DdT’s reproduced Op. 1 title page gives `M.D.C.XCVI`. DdT’s preface says it reproduces the original title pages. Identify the consulted object and distinguish a transcribed date from a supplied bibliographic date. [Library catalogue](https://www.finna.fi/Record/uniarts_print.994948484206249), [DdT title-page OCR, image 11](https://api.digitale-sammlungen.de/ocr/bsb00023199/11), [DdT preface OCR, image 8](https://api.digitale-sammlungen.de/ocr/bsb00023199/8).

2. **Make the relationship between the continuo line and the keyboard realization explicit.** The [initial score definition](../../../11_buxtehude_sonatas_final/buxtehude_op1_01_sonata_f_major_corr.mei) has five staves: violin, gamba, continuo bass, and a separate two-staff keyboard part. Its lower group has an empty label and neither lower staff has a label. CAMAT currently names these two parts `f11qk4ip` and `p1wqsc4n`, because its mapper reads individual staff labels and falls back to IDs; a group label alone will not solve this consumer issue.

   Document the origin and function of staves 4–5, confirm the realization’s attribution, and provide stable part roles that distinguish source continuo from realized keyboard texture. Give individual staves usable labels under the project’s display policy, or teach CAMAT to interpret the group and role metadata. The three entries in `perfMedium` need not become five instruments: multiple staves can represent one resource. Link performance resources to staff definitions where useful.

   This affects analysis substantially: staves 4–5 contain 2,873 of the 6,858 written note elements, about 41.9%. An unfiltered pitch or texture analysis therefore includes the realization. Preserve it in the edition, but make an explicit choice about its inclusion in an analysis view. Existing MIDI programs are also all `0`; they do not provide reliable instrument identity.

3. **Complete and preserve event IDs.** Three notes lack `xml:id`, at [line 1026](../../../11_buxtehude_sonatas_final/buxtehude_op1_01_sonata_f_major_corr.mei), [line 1249](../../../11_buxtehude_sonatas_final/buxtehude_op1_01_sonata_f_major_corr.mei), and [line 1250](../../../11_buxtehude_sonatas_final/buxtehude_op1_01_sonata_f_major_corr.mei). Their surrounding chord at [line 1024](../../../11_buxtehude_sonatas_final/buxtehude_op1_01_sonata_f_major_corr.mei) also lacks an ID. This is schema-valid but prevents complete event-level addressability in CAMAT. Require IDs for independently referenced musical events; preserve existing IDs through later corrections. Identify events across the corpus by stable file identifier plus fragment ID. Repeated IDs in separate XML files are not inherently invalid.

4. **State precisely what “corrected” means.** The header describes reproduction of DdT with corrected OMR errors, but measures 11 and 97 deliberately depart from DdT’s notation. Revise the policy to distinguish recognition/conversion repair, preservation of historical editorial interventions, and new CAMAT emendations. The three existing annotations are useful and need not be replaced wholesale. Add verified responsibility and source pointers, and define project categories separating an emendation from an encoding/rendering comment. MEI provides `annot/@resp`, `annot/@source`, and `@type` for these purposes. [MEI annotation reference](https://music-encoding.org/guidelines/v5/elements/annot.html).

   For users who must reconstruct both readings, consider `choice/sic/corr`, or `app/lem/rdg` for witness variants. Treat this as a product decision: alternatives need an explicit selection policy in both rendering and CAMAT extraction. A documented corrected reading plus an addressable annotation can be sufficient for the first corpus release. [MEI scholarly-editing guidance](https://music-encoding.org/guidelines/v5/content/scholarlyediting.html).

5. **Finalize file identity and release metadata together.** The publication URI still points to a `_corr.mei` file on mutable `main`, while the workflow calls for dropping `_corr`. The `altId` also uses the shorter `op1_01_…` identifier rather than the full filename stem. Either define that as a deliberately independent local key or make the naming rule consistent. At release, coordinate filename, canonical URI, edition version, publication date, and reviewed status. Retain a convenient current URL, and add an immutable release/commit reference and preferably an archival persistent identifier. An edition number of `1.0.0` should describe a real release, not a template default.

6. **Strengthen the release gate beyond the current green report.** The repository workflow executes RELAX NG, but I found no execution of the embedded Schematron in the inspected Python validators. Checking for a Schematron processing instruction is not executing its rules. Make the separate execution performed in this assessment part of the normal gate.

   Temporary negative probes also exposed concrete gaps in [the project checker](../../../scripts/check_mei_consistency.py): it returned zero findings after replacing a revision responsibility with a nonexistent ID, replacing both schema URLs with version 4.0.1 URLs, or removing the digital-file license while leaving the source-image license. Scope metadata requirements to the correct header paths, compare the full schema URL/version, and cover `resp` and `source` in reference checks. These are checker limitations; the pilot’s actual responsibility references and separate license statements are present and valid.

**Useful additions, in order of value**

- Expand `editorialDecl` with concise normalization and interpretation rules: written versus sounding accidentals, courtesy accidentals, clefs/transposition, ornaments, cross-staff/layer semantics, and source versus editorial brackets and question marks. The file has 713 `accid.ges` attributes; define their intended meaning rather than stripping them as export noise. Figured-bass strings include both `#` and `♯`, plus parenthesized and questioned figures. Establish whether these are source typography, source uncertainty, or modern intervention. Preserve source readings while making any analytical normalization explicit. [MEI normalization](https://music-encoding.org/guidelines/v5/elements/normalization.html).
- State the segmentation policy. The file has one `section`, with seven tempo regions beginning at measures 1, 28, 34, 74, 86, 126, and 137. If CAMAT needs segment-based analysis, provide stable section identifiers or a segment index grounded in the work’s musical organization. A tempo change alone need not define a separate movement. [MEI segmentation](https://music-encoding.org/guidelines/v5/elements/segmentation.html).
- Preserve work-local page numbering, and add printed page labels directly on surfaces where useful. Document that zones use the resized graphic’s coordinates: the first graphic is 4,134 × 5,495 pixels, whereas its IIIF canvas is 5,746 × 7,638. This is not itself an error, but exporting zones to canvas coordinates requires scaling. Also state the coordinate boundary convention.
- Add controlled genre and performing-medium terms only where they support queries. Include sourced composition/publication chronology with uncertainty; do not treat the 1903 source-edition date as the work’s creation date. Contributor ORCIDs and structured funding are useful when verified. A larger header is not automatically better metadata.
- Publish a corpus-level manifest containing stable file/work IDs, release paths, hashes, status, source pages, profile version, and documented omissions or exceptions. Add `CITATION.cff` and an archived release; keep validation software versions and results with that release. These complement per-file headers and support persistent identification, provenance, and reuse. [FAIR principles](https://www.gofair.foundation/fair-principles), [Citation File Format](https://github.com/citation-file-format/citation-file-format).
- Keep raw OMR files traceable through a manifest or source links, and define status transitions and meaningful version increments. Header revision history should record scholarly milestones; Git can retain routine edits. Do not invent unavailable dates or responsibilities to fill template fields.

**How the reference corpora inform this recommendation**

The list is valuable for parser coverage, but includes different MEI versions and editorial purposes. Five representative headers were retrieved; this was not a survey of every linked file.

- The [MEI 5.1 Altenburg example](https://raw.githubusercontent.com/music-encoding/sample-encodings/main/MEI_5.1/Music/Complete_examples/Altenburg_Concerto_C-major.mei) illustrates authority metadata, work classification, performing resources, and conversion provenance. Your source and facsimile links already serve this edition well; borrow only fields that answer useful corpus questions.
- The [CRIM example](https://raw.githubusercontent.com/CRIM-Project/CRIM-online/master/crim/static/mei/MEI_4.0/CRIM_Model_0001.mei) separates work classification from historical manifestation metadata. That distinction is useful, but does not require replacing your compact `sourceDesc` structure.
- The [Freischütz Digital core example](https://raw.githubusercontent.com/Freischuetz-Digital/data-music/master/ready-for-use/core/core_mov0.xml) provides a useful model for edition versions and repository/archive identity. Its older MEI syntax should not be copied into a 5.1 template.
- The [Measuring Polyphony example](https://raw.githubusercontent.com/MeasuringPolyphony/measuring_polyphony_jekyll/master/assets/mei/305.mei) explicitly explains rhythmic normalization and source comparison. That is a good editorial-policy lesson. The retrieved file also repeats `xml:id="KD"`, illustrating why reference files need independent validation.
- The [TROMPA Beethoven example](https://raw.githubusercontent.com/trompamusic-encodings/Beethoven_Op119_BreitkopfHaertel/master/Beethoven_Op119_Nr01-Breitkopf.mei) has a comparatively small conversion-oriented header. It is useful for interoperability testing, but is not a completeness target for a scholarly corpus release.

Keep the final model as **official CMN + a documented CAMAT profile + automated profile checks + editorial sign-off**. Prioritize truthful source/reading provenance and analytically distinguishable musical content over additional optional bibliographic detail.
